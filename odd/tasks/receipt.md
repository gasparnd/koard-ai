# Verifiable receipt tied to the reviewed candidate

Objective: issue an immutable, digest-verifiable receipt the moment a review lifecycle settles `approved`, and expose a way to re-verify it against the currently persisted lifecycle and snapshot. Branch: `task/2.6-receipt`, stacked on `task/2.5-independent-review`. Delivery: inline, single work unit. Test runner: `go test` and `go vet`.

## Specs

1. S1 — Roadmap outcome: "Verifiable receipt tied to the reviewed candidate." (`docs/roadmap.md`, Receipt-driven development section).
2. S2 — User continuation: "Dale, arranquemos con ese milestone" — the next unchecked roadmap item after milestone 2.5 (independent review with bounded correction).
3. S3 — Verification mechanism: user selected "Binding por digest (Recomendado)". The receipt is a versioned JSON record binding the exact target, verdict, reviewer, and correction budget used, identified by the SHA-256 digest of its own canonical content — the same pattern as every other artifact in this codebase (`candidate.Candidate`, `snapshot.Manifest`, `consent.Record`). No cryptographic signing, no key management, no external trust anchor.
4. S4 — Issuance: a receipt is issued automatically, as part of the review lifecycle itself, exactly when and only when a lifecycle settles with state `approved` — from the initial attempt or after the one permitted correction. No separate user action or new consent authorizes it. No other terminal state (`rejected`, `failed`, `escalated`) ever gets one.
5. S5 — Location and immutability: the receipt is `review/receipt.json`, write-once like every other lifecycle artifact.
6. S6 — Content: the exact `Target` (workflow, candidate, snapshot, risk tier), the approved verdict's reviewer identity, the attempt number, and the correction budget used out of the max — everything a future controlled-mutation layer needs to confirm before ever touching the workspace.
7. S7 — Verifiability: a read-only function recomputes the receipt's own digest from its persisted content (tamper detection) and cross-checks its `Target` against the currently stored, validated review lifecycle and the snapshot it names (reading the correction snapshot directory instead of the original when the receipt's attempt is 2) — fails closed on any mismatch, missing state, or corrupted content.
8. S8 — Non-mutation boundary: issuing or verifying a receipt never applies files, mutates the workspace, or authorizes commit, push, pull request, merge, or release. It only proves a candidate passed the required path; it never acts on that proof.
9. S9 — CLI: fold receipt visibility into the existing `koard review status` / `koard review run` output (one added `receipt: <id>` line when approved) rather than a new subcommand — decided during exploration as the minimal consistent extension.
10. S10 — Tests: cover issuance exactly on approval (initial attempt and after a correction), absence on every other terminal state, tamper detection, target-mismatch detection, re-verification against a corrupted snapshot, and CLI exposure.
11. S11 — Docs: new `docs/receipt.md` (and its entry in `docs/README.md`'s index), plus `architecture.md`, `independent-review.md` cross-reference, `roadmap.md`, and `README.md`. Run focused race tests, `go test ./...`, `go vet ./...`, `gofmt -l internal cmd`, and `git diff --check`.
