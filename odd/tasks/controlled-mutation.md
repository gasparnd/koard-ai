# Controlled mutation

Objective: the first real workspace-write capability in Koard. Apply the exact, receipted, non-stale candidate snapshot to the real workspace, atomically and idempotently, with no git authority whatsoever. Branch: `task/2.6-receipt` (continues the stacked chain; renaming to a 3.x branch is a later housekeeping concern, not a blocker). Delivery: inline, single cohesive work unit covering all four roadmap bullets at once — the simplest design that satisfies partial-write safety also satisfies idempotency and recovery, so splitting them apart would be artificial. Test runner: `go test` and `go vet`.

## Specs

1. S1 — Roadmap outcome, four bullets in `docs/roadmap.md`'s "Controlled mutation" section:
   - "Apply only the exact candidate snapshot that completed the required RDD path."
   - "Handle partial writes, interruption, and recovery deterministically."
   - "Keep commit, push, pull request, merge, and release outside receipt authority."
   - "Verify replay, idempotency, and recovery when the Koard process dies mid-run."
2. S2 — User continuation: "Dale, arranquemos con controlled mutation" — the next, and last, roadmap section after "Receipt-driven development" closed in full.
3. S3 — Authorization gate: user selected "Receipt solo (Recomendado)" over an additional explicit confirmation flag. A valid, non-stale, approved `review.ReceiptStatus` is sufficient authority to apply — consistent with how authority already lives in persisted artifacts (consent grants, correction decisions) rather than interactive prompts everywhere else in this codebase.
4. S4 — No capability negotiation: Apply is not mediated through the handoff/provider/capability system at all. Nothing untrusted decides what to write — the content is already the exact, already-reviewed snapshot bytes. `mutation.CapabilityWorkspaceWrite` and friends stay reserved and unused; they describe a different, later concern (a model-driven role requesting to write), not this one.
5. S5 — Mechanism: for every entry in the receipted snapshot's manifest, read it (`snapshot.ReadEntry`, re-verifying its digest), then write it to `workspace/<relative path>` atomically (temp file in the same directory, then rename) — creating parent directories as needed. The snapshot directory is the original capture for attempt 1, the correction capture for attempt 2 (same selection `ReceiptStatus` already makes; extract and reuse one shared helper instead of a third inline copy).
6. S6 — Idempotency and recovery by construction, not a journal: content is deterministic from the snapshot, and each file's write is atomic, so re-running Apply after any interruption — mid-file, between files, or after full completion — simply re-verifies and re-writes every entry, converging to the identical correct end state every time. A completion marker (`apply.json`, mutable like `workflow.json` rather than write-once like every other artifact here) records the fact once all entries are confirmed written, and a repeat call whose marker already matches the current receipt's target short-circuits without re-touching the filesystem.
7. S7 — Non-authority boundary: Apply never invokes git in any form — no stage, commit, push, pull request, merge, or release. It only ever writes ordinary files inside `workspace`. Verified by an executable test inside a real git repository asserting no staged or committed change results from Apply.
8. S8 — Path safety: reuse (not re-derive a third time) the exact canonical-relative-path validation `snapshot.readArtifact`/`Materialize` already apply, exported once for this new caller, since this is the first place that validation protects a write into the real, permanent workspace rather than a disposable temp directory.
9. S9 — CLI: `koard review apply --workflow <id>`, consistent with the existing `review run/status/correction` family since all the state apply depends on already lives there. `koard review status`/`run` gain one `apply: applied` line once a completed apply record exists.
10. S10 — Tests: apply only with a valid non-stale receipt (refuses otherwise, no file written); writes the exact receipted bytes to their declared paths; a second call is a safe no-op; a simulated mid-run interruption (some files written, no completion marker yet) recovers correctly on the next call; no `.git` state changes result; path-safety rejection; corrupted-snapshot rejection before any write.
11. S11 — Docs: new `docs/controlled-mutation.md`, its entry in `docs/README.md`'s index, `architecture.md`, `independent-review.md` cross-reference, `roadmap.md`, `README.md`. Run focused race tests, `go test ./...`, `go vet ./...`, `gofmt -l internal cmd`, and `git diff --check`.
12. S12 — Risk: this is the project's first irreversible-effect capability (CLAUDE.md high-risk item 1 — data/effects that cannot be rebuilt). The commit implementing it is explicitly escalated for native review regardless of the assess tool's own budget-based gating.
